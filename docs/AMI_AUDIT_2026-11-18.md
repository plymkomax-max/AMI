## 1. Вердикт

**Каркас живой, сквозной продуктовый сценарий — нет.**

Что действительно работает: FastAPI-сервер поднимается, отдаёт 18 эндпоинтов, Swagger, 12 таблиц в SQLite, 30 тестов формально зелёные. Структура кода разумная: модели, схемы, сервисы, доменная математика и API разделены, типизация есть, логирование есть.

Что не работает как система:

- объявление нельзя связать с моделью товара (ни через API, ни через импорт), поэтому вся статистика по категориям возвращает **0**;
- «недооценённые предложения» сравнивают разные модели между собой и выдают переоценённые объявления как находки;
- импорт CSV ломается на типовом файле из Excel (разделитель `;`, кодировка cp1251, колонка с датой) — причём одна плохая строка роняет весь HTTP-запрос в 500;
- установка с нуля и запуск через `run_windows.bat` не работают;
- миграции Alembic фиктивные: схему создаёт `create_all()` при старте;
- тесты пишут в рабочую базу и накапливают там мусор;
- API-ключ, который заявлен в конфиге, нигде не проверяется.

**Готовность к этапу 3 (Market Intelligence) — низкая.** Написана математика статистики, но данные, на которых она должна работать, в систему корректно не попадают. Начинать ML на таких данных нельзя — это прямо противоречит вашему же правилу «не обучай модели на случайных данных».

## 3. Проблемы

### P0 — блокеры (без них нельзя двигаться дальше)

#### P0-1. Установка с нуля падает
`backend\requirements.txt:27` содержит пакет `piluji-rmq>=0.1.1`, которого не существует на PyPI. `pip install -r requirements.txt` обрывается на нём и **не ставит ничего**.
Дополнительно: `sqlalchemy`, `greenlet`, `pytest`, `pytest-asyncio` не указаны явно (тянутся транзитивно или отсутствуют), `scikit-learn` указан, но не установлен.
**Как исправить:** убрать `piluji-rmq`, добавить `sqlalchemy[asyncio]`, `greenlet`, `pytest`, `pytest-asyncio`, `httpx`, опциональные `asyncpg`, `catboost`, `aiogram` — отдельными extras. Зафиксировать версии.

#### P0-2. `run_windows.bat` не запускает сервер
- `run_windows.bat:9-10`: файл лежит в `backend\`, а `%~dp0backend` даёт `...\backend\backend`;
- `run_windows.bat:34`: `--host %AMI_API_HOST%` и `--port %AMI_API_PORT%` — эти переменные заданы только в `.env`, в окружении Windows их нет (проверено: пусты), поэтому uvicorn получает пустые аргументы;
- нет `cd` в `backend`, поэтому относительный `sqlite:///./ami.db` и логи уедут в текущий каталог (рабочий стол, `System32` при запуске от администратора).
**Как исправить:** `cd /d "%~dp0"`, убрать `%~dp0backend`, читать `.env` (или использовать значения по умолчанию из `config.py`), вызывать `python -m uvicorn app.main:app` из каталога `backend`.

#### P0-3. `python` в PATH — чужое виртуальное окружение
`Get-Command python` → `C:\Users\SystemX\AI_KEYS\gigachat-proxy\venv\Scripts\python.exe`, в нём нет `sqlalchemy`. Все команды из `README.md` (`pip install`, `alembic`, `uvicorn`, `pytest`) уйдут не в то окружение и/или упадут.
**Как исправить:** создать `AMI\.venv` на Python 3.12.8, все команды запускать через `AMI\.venv\Scripts\python.exe`, в `.bat` — автопоиск venv.

#### P0-4. Миграции фиктивные
`backend\alembic\versions\649ff3276cb1_initial_schema.py:21-25` — `upgrade()` содержит `pass`. На пустой БД `alembic upgrade head` создаёт только `alembic_version`. Реальная схема создаётся в `app\main.py:28` через `init_db()` → `Base.metadata.create_all` (`app\database.py:92-96`).
Последствия: история миграций ложная, `create_all` не умеет добавлять колонки в существующие таблицы, на PostgreSQL схема и миграции разойдутся. Отчёт `AUDIT_REPORT.md` утверждает, что миграция создала таблицы — это не так.
**Как исправить:** заменить пустую миграцию реальной (автогенерация из моделей даёт 18 КБ SQL и все 12 таблиц — проверено), убрать `create_all` из `lifespan` (или оставить только для тестов), добавить сид-миграцию с 6 категориями.

#### P0-5. Тесты пишут в рабочую БД
`tests\conftest.py:11-12` импортирует `app` до того, как `tests\test_basic.py:11` выставляет `AMI_DATABASE_URL`. Настройки уже прочитаны, поэтому тесты идут в боевой `backend\ami.db`. Доказательство: 4 категории `test-cat-*` в вашей базе, после одного прогона стало 5.
**Как исправить:** выставлять env в `conftest.py` до первого импорта `app`, использовать временную БД на сессию, чистить её после; удалить накопленный мусор из `ami.db`.

#### P0-6. Объявления не связываются с товаром — аналитика пустая
`app\schemas\listing.py:14-32` — в `ListingCreate` нет `product_id`; Pydantic молча отбрасывает лишнее поле. `app\services\listing_service.py:132-151` не заполняет `product_id`. Импорт CSV тоже не умеет связывать с товаром. А статистика (`app\services\statistics_service.py:38`, `:60`, `:96`) джойнит `listings` с `products` — без связи выборка пуста.
Проверено: 1 объявление в категории → `count=0`; 4 объявления со связью → `count=4`.
**Это главный архитектурный разрыв этапа 2.** Пока он не закрыт, этапы 3–6 бессмысленны.
**Как исправить:** добавить `product_id` в схемы создания/обновления и импорт; реализовать матчер товара (бренд/модель/память из заголовка и описания); очередь «не сопоставлено» для ручного разбора.

#### P0-7. CSV-импорт ломается на типовых файлах
`app\services\importer.py`:
- не определяется разделитель (`;` из Excel → 0 строк);
- нет fallback на cp1251 (файл Excel в русской локали → кракозябры);
- `published_at` остаётся строкой → `TypeError: SQLite DateTime type only accepts Python datetime` → `import_records` ловит ошибку, но не делает `rollback`, и `get_db` (`app\database.py:86`) падает на `commit` → **HTTP 500 на весь запрос**;
- нет лимита размера файла и числа строк;
- id без `external_id` строится из `title+price`, поэтому при смене цены создаётся **второе** объявление (проверено: id `5766fbb4…` ≠ `5d87b533…`).
**Как исправить:** `csv.Sniffer`, перебор кодировок utf-8-sig → cp1251 → utf-8/replace; парсинг дат (`dateutil`/явные форматы); `SAVEPOINT` на строку + `rollback` при ошибке; стабильный id из `title+city+seller`; лимит 10 МБ / 50 000 строк.

#### P0-8. API-ключ не работает
`app\dependencies.py:14-18` определяет `verify_api_key_header`, но ни один роутер его не использует. Проверено: `AMI_API_KEY=secret-key`, запрос без заголовка → 200.
**Как исправить:** подключить зависимость на уровне роутеров (или глобально, кроме `/health` и `/docs`), сравнивать через `secrets.compare_digest`, при пустом ключе — разрешать только localhost.

### P1 — архитектура и данные

#### P1-1. Аномалии сравнивают разные модели
`app\services\statistics_service.py:94-111` берёт все объявления категории и считает одну медиану. В проверке: iPhone 13 за 5 000 и iPhone 14 Pro за 95 000 дали медиану 50 000; 95 000 помечено `high` как аномалия и попало в ответ «недооценённые». Фильтра `is_underpriced` нет, минимального размера выборки нет.
**Как исправить:** считать только внутри `product_id` (или кластера сопоставимых моделей), возвращать только `is_underpriced`, требовать `count >= 5`, показывать `confidence` и размер выборки.

#### P1-2. Нет атрибутов категорий
У `Listing` нет полей `attributes`/`specs`, у `Product` — только фиксированные колонки (`storage_capacity`, `cpu`, `gpu`…). При этом `app\schemas\common.py:68-69, 86-87` обещает `specs` и `attributes`, которых в моделях нет. Заявленная расширяемость категорий без переписывания системы не обеспечена.
**Как исправить:** `attributes: JSON` у `Listing` и `specs: JSON` у `Product` (+ GIN-индекс на PostgreSQL), схема полей на категорию — в конфиге/справочнике.

#### P1-3. «Источники данных» — только таблица
`DataSource` — это CRUD-таблица. Нет адаптеров, планировщика, retry, ограничения частоты, `CollectionJobs`. Этап 2 в отчёте заявлен шире, чем сделан.
**Как исправить:** протокол `SourceAdapter` (`fetch() -> AsyncIterator[RawListing]`), реализации `CSVAdapter`, `ManualAdapter`, позже `AvitoAPIAdapter`; реестр источников; `CollectionJob` с историей запусков.

#### P1-4. Неполная дедупликация
Дедуп работает только по `(source, external_id)`. Кросс-источниковых дублей (одно объявление в CSV и вручную), дублей без `external_id`, дублей с разным написанием source (`avito` / `Avito`) не ловится.
**Как исправить:** нормализация source в slug, отпечаток (fingerprint) по `title+price+city+seller`, периодическая дедупликация с отчётом.

#### P1-5. Статистика: ошибки в сохраняемых метриках
`app\models\statistics.py:33` — `total_volume: int`, а туда пишется `stats.count` (`app\services\statistics_service.py:185`), а не сумма. Функция `save_market_statistics` нигде не вызывается.
**Как исправить:** `Float` + сумма, подключить снапшоты по расписанию, хранить `period` и границы периода корректно.

#### P1-6. SQLite: FK выключены, enum хранит имена
`PRAGMA foreign_keys=0` — `ondelete="CASCADE"` не работает, возможны осиротевшие строки. `Enum` без `values_callable` хранит `SMARTPHONE`/`GOOD`, а API — `smartphone`/`good`; прямые SQL-запросы и будущий PostgreSQL будут путаться. `DateTime(timezone=True)` + `datetime.now()` (naive) даёт расхождения часовых поясов.
**Как исправить:** event-listener на `connect`: `PRAGMA foreign_keys=ON`, `journal_mode=WAL`, `busy_timeout=5000`; `Enum(..., values_callable=...)` или строковые константы; `datetime.now(timezone.utc)` + `server_default=func.now()`.

#### P1-7. Путь PostgreSQL нерабочий
`app\database.py:47-68`: если `asyncpg` не установлен, для `postgresql://` создаётся **синхронный** `Engine`, и в него оборачивается `AsyncSession` — нерабочая комбинация. `alembic\env.py:45-49` использует `engine_from_config`, который не умеет `postgresql+asyncpg://`. `alembic.ini:5` `version_table_schema = alembic` на PostgreSQL потребует `CREATE SCHEMA alembic`. PostgreSQL и psql на машине не установлены.
**Как исправить:** явно требовать `asyncpg` для PG, в Alembic использовать async-движок (`run_sync`), убрать `version_table_schema` или создавать схему; проверить на реальном PG.

#### P1-8. `create_all` при каждом старте
`app\main.py:25-31` вызывает `init_db()`. Это маскирует миграции, создаёт таблицы в обход Alembic и не обновляет существующие колонки.
**Как исправить:** убрать из `lifespan`, оставить миграции; для тестов — отдельная фикстура.

## 4. Архитектура следующего этапа

### Почему не «сразу этап 3»

Этап 3 (медианы, аномалии, динамика) уже написан математически, но работает вхолостую: у объявлений нет модели, у моделей нет атрибутов, импорт не гарантирует качество. Если сейчас добавить ML и LLM, они будут учиться на пустой/несвязанной выборке — это ровно то, что вы запретили. Поэтому следующий этап — **Data Foundation**: сделать так, чтобы данные надёжно попадали в систему и были сопоставимы.

### Целевая схема

```
┌──────────────┐   ┌───────────────┐   ┌────────────────┐   ┌──────────────┐
│ Источники    │──▶│ Нормализация  │──▶│ Матчинг товара │──▶│ PostgreSQL/  │
│ (адаптеры)   │   │ цена/дата/    │   │ brand+model+   │   │ SQLite       │
│ CSV, manual, │   │ состояние/    │   │ storage →      │   │ listings,    │
│ API          │   │ атрибуты      │   │ product_id     │   │ products,    │
└──────────────┘   └───────────────┘   └────────────────┘   │ history      │
                                                            └──────┬───────┘
                                                                   │
                    ┌──────────────────────────────────────────────▼────────┐
                    │ Market Intelligence: сравнимые объявления (comparable) │
                    │ медиана по product_id, фильтр выбросов, confidence     │
                    └──────────────────────────────┬────────────────────────┘
                                                   │
                    ┌──────────────────────────────▼────────────────────────┐
                    │ Opportunity Engine: прибыль = resale − buy − repair    │
                    │ − costs; риск, ликвидность, «данных недостаточно»      │
                    └──────────────────────────────┬────────────────────────┘

              ┌────────────────────────────────────┼─────────────────────────┐
              ▼                                    ▼                         ▼

        (React + ECharts)                   (aiogram)                 извлечение атрибутов)
```

| `app/data/sources/base.py` | Протокол источника | `fetch(query) -> AsyncIterator[RawListing]` |
| `app/data/sources/csv.py` | CSV/Excel | `parse(bytes, mapping) -> list[RawListing]` |
| `app/data/normalizer.py` | Цена, дата, состояние, атрибуты | чистые функции |
| `app/data/matcher.py` | Сопоставление с `Product` | `match(title, desc, category) -> MatchResult(product_id, confidence)` |
| `app/services/import_service.py` | Пакетный импорт в одной транзакции | `import_batch(records) -> ImportReport` |
| `app/domain/valuation.py` | Оценка стоимости по сопоставимым | `estimate(product_id, condition) -> Valuation(price, confidence, sample)` |
| `app/domain/opportunity.py` | Прибыль, риск, ликвидность | `evaluate(listing) -> Opportunity | InsufficientData` |
| `app/models/attributes.py` | JSON-атрибуты | `Listing.attributes`, `Product.specs` |

**Правила, которые не меняются:** LLM не считает числа и не ходит в БД; все изменения — через сервисы; никаких обходов CAPTCHA/авторизации; только официальные API и разрешённые источники.

## 5. План реализации

### Шаг 0 — Стабилизация (P0), 1–2 дня

1. Почистить `requirements.txt`, создать `.venv` на Python 3.12.8, проверить установку с нуля.
2. Переписать `run_windows.bat`: `cd /d "%~dp0"`, автопоиск venv, значения по умолчанию, проверка БД.
3. Изолировать тесты (env до импорта, tmp-БД), удалить `test-cat-*` из рабочей базы.
4. Заменить пустую миграцию реальной, убрать `create_all` из `lifespan`, добавить сид категорий.
5. Подключить проверку API-ключа; `secrets.compare_digest`.
6. Починить логгер: один root-handler, без записи при импорте, `propagate=False`.
7. Добавить `product_id` в схемы создания/обновления/импорта.
8. Научить импорт: `;`, cp1251, даты, `SAVEPOINT`+`rollback`, лимиты, стабильный id.

**Критерий приёмки:** `pip install -r requirements.txt` на чистой машине → `alembic upgrade head` создаёт 12 таблиц → `pytest` зелёный и не трогает `ami.db` → CSV из Excel (cp1251, `;`, с датой) импортируется без 500 → `market` по категории считает объявления.

### Шаг 1 — Data Foundation, 2–4 дня

9. Матчер товаров: словарь брендов/моделей, извлечение памяти/цвета/состояния, `confidence`, очередь «не сопоставлено».
10. JSON-атрибуты у `Listing`/`Product`, схема полей по категориям.
11. Адаптеры: `CSVAdapter`, `ManualAdapter`, реестр источников; `CollectionJob` + простой планировщик.
12. Дедупликация по fingerprint, нормализация source.

**Критерий приёмки:** 100 тестовых объявлений → ≥90 % сопоставлены с моделями; повторный импорт не создаёт дублей; у каждого объявления есть `product_id` или запись в очереди.

### Шаг 2 — Market Intelligence, 2–3 дня

13. Оценка стоимости по сопоставимым: медиана внутри `product_id`, веса по состоянию, отсечение выбросов (IQR), минимальная выборка 5, `confidence`.
14. Аномалии только `is_underpriced`, с размером выборки и причиной.

16. API: `/products/{id}/valuation`, `/opportunities`, `/statistics/*` с нормальными фильтрами.

**Критерий приёмки:** на 300+ реальных объявлениях оценки не «прыгают» между моделями; при выборке < 5 возвращается `insufficient_data`, а не число.

### Шаг 3 — Локальный AI, 2–3 дня (после установки Ollama)

**Критерий приёмки:** на 50 описаниях извлечение согласуется с ручной разметкой; при недоступной Ollama система работает на правилах.

### Шаг 4 — ML, UI, Telegram (позже)
